系统层：为什么需要 RL-Kernel

算法对了，系统仍可能把 ratio 算脏。这一页解释 train–inference 数值不一致，以及算子库站在哪一层。

一条 RL 步在干什么

  1. Rollout：vLLM / sglang 按当前策略采样 token，顺带记下 old_logprob。
  2. 奖励：规则、裁判模型或 RM 给整段回复打分。
  3. 训练：Megatron / FSDP 对同一条序列重算 logprob，做 GRPO/PPO 损失，反传。
  4. 同步：新权重拷回 rollout 引擎。

verl、slime、vime 做 1–4 的调度。RL-Kernel 只替换其中最贵、最容易漂的算子：selected-logprob、线性层融合、packing、确定性 GEMM / attention。

Selected logprob

训练几乎从不对整个词表做 CE。它只要「实际采样到的那个 token」的 log π：

logπ(y_t | y_<t) = logit[y_t] − logsumexp(logits)

朴素实现会物化 [B, S, V] logits。V≈15 万、G=64 时显存爆炸。Fused linear logp 从 hidden 和 LM head 权重直接流式算出 selected logp，不落地完整 logits。

漂移从哪来

来源现象
Batch size / packing同一条序列单独算和塞进大 batch 算，logp 差 1e-3
Split-K GEMM、cuBLAS 选核形状一变，归约顺序变
Attention split-KV / chunked prefillsoftmax 累加顺序变，LSE 变
TP/CP 归约多卡 all-reduce 顺序、downcast 时机不同
Tokenizer / padding 左右根本不是同一条序列，后面全白比

算法同学看到 KL 慢慢爬，容易怪奖励或超参。先查 dlogp = train_logp − old_logp 在更新权重之前是不是已经非零。

RL-Kernel 的定位：算子级 train–inference 一致性，不是「第一个 batch-invariant kernel」（那些已经有 Thinking Machines / sglang / DeepSeek）。也不是框架级对齐（那是 vime / verl）。

Batch-invariant 是什么意思

固定模型、固定序列、固定权重：输出不随 batch=1/N、padding、chunked-prefill 开/关而变。Bitwise 最好，否则走公开的容差合同。

单卡链：RMSNorm → GEMM → Attention → LM head → logprob。多卡再锁 TP/CP 归约顺序。真 vLLM == 真 Megatron 是再下一阶段。

和 vLLM handbook 的关系

vLLM 站在 inference serving。RL-Kernel 站在 post-training 热路径。两者在 rollout 相遇：vLLM 负责快采样，RL-Kernel 负责采样出的 logprob 能被训练侧复现。
