系统层：为什么需要 RL-Kernel

算法对了，系统仍可能把 ratio 算脏。这一页讲 selected logprob 怎么算、数值从哪漂、算子库站在哪一层。

三层各管什么

层例子职责
编排verl、slime、vime、TRL、OpenRLHF采样、奖励、权重同步、数据切分、hybrid 调度
引擎vLLM / sglang；Megatron / FSDP / DeepSpeed推理生成；训练前向反传
算子RL-Kernel替换 logprob / GEMM / attention / packing 这些热路径，锁归约顺序

RL-Kernel 不拥有 RL 框架。它经 custom op / 可选 backend 插进去；关掉时纯推理不受影响。官方项目文档在 rl-align.github.io/RL-Kernel；下面把算子合同写在这里，不必跳出去才能懂。

Selected logprob

训练几乎不对整个词表做交叉熵。它只要「实际采到的那个 token」的对数概率：

logπ(y_t | y_<t) = logit[y_t] − logsumexp_v(logit[v])

两段式朴素路径：

  1. LM head：logits = hidden @ Wᵀ → 形状 [N, V]，V≈10⁵–1.5×10⁵。
  2. log_softmax 再 gather 出 target。

GRPO 再乘 group size G。显存按 G · L · V 涨。A100 上 G=256 时，TRL 式物化经常直接 OOM；把 logits 拆成词表块流式做 online softmax，额外显存接近常数。

算子输入不落地什么
fused logp已经有的 [N,V] logits + target id完整概率矩阵；仍要先有 logits
linear logphidden [N,D]、LM head W [V,D]、target id整段 [N,V] logits（前向流式）
batch-invariant logplogits + target不追求省显存，追求归约顺序与 batch 无关

linear logp 的前向：把词表切成块，每块做一小段 GEMM，用 online softmax 维护 (m, s) = (max, Σ exp(z−m))，最后 z_target − (m + log s)。反向要么重算 tile（省激活），要么在 SM90 上留局部 workspace。输出固定 fp32，梯度回 hidden 和 W。

词表 TP：每张卡只有 W 的一段。各卡先算局部 (max, sumexp, 本卡是否持有 target)，再按固定的 shard 下标顺序合并 LSE，而不是把 NCCL sum 当数值归约器。

Online softmax 和归约顺序

logsumexp 对交换律在实数上成立，在浮点上不成立。两段相同的数，先加左边还是先加右边，最后一位可以不同。cuBLAS 还会按形状换 kernel、上 split-K：batch 一变，同一行的累加拓扑就变。

Batch-invariant 的合同：固定一行 logits 和 target id，单独算、放进大 batch、换 padding、chunked prefill 开/关，这一行的 logp 必须一样（bitwise，否则走公开容差）。做法是每行自己的树状归约，禁止 atomicAdd 把别的行搅进来，Triton 关掉 autotune。

Attention 同理。训练常用整段 softmax；推理常用 chunked prefill / paged KV。Online softmax 合并的是 (out, lse)，按 逻辑 global_block_index 排，不能按 ring 到达顺序排。Split-KV 会再引入一条归约轴，严格模式关掉它。

漂移从哪来

诊断量（只在 response token 上，更新权重之前）：

dlogp = train_recomputed_logp − rollout_old_logp
来源现象
Tokenizer / padding 左右 / 特殊 token根本不是同一条序列
Batch size、pack vs pad同一行因邻居行不同，GEMM/softmax 换核
Split-K、TF32、非确定 all-reduce累加顺序随形状和拓扑变
Chunked prefill、prefix cache、decode vs 整段attention LSE 合并顺序变
TP/CP：downcast 发生在通信前还是后局部 bf16 再加，和全局 fp32 再下铸，不是同一个数
采样时乘了温度，训练时又乘一次比的不是同一个 π

KL 曲线往上爬，先看 dlogp 在 step 0 是不是已经非零。非零就不是算法，是基础设施。

算子级一致性：我们自己的 op 链在 batch、padding、并行配置下自洽。框架级一致性：vime / verl 对齐数据流。真 vLLM == 真 Megatron 是再下一层，两边都正确仍可能差 ~1e-3，要逐层探针。

前向链上每一段

单卡要锁的链：

embedding → RMSNorm → QKV GEMM → RoPE → attention → MLP GEMM
         → RMSNorm → LM head / linear_logp → selected logp
  • RMSNorm：行内归约。顺序不锁，dweight 会随 chunk 切分变。
  • det GEMM：cuBLAS 不保证 batch-invariant。固定 K 循环、fp32 累加、禁止 split-K。
  • Attention：禁止 split-KV；导出 attention-domain LSE（不是 vocab LSE）。
  • RoPE / 逐点：本身不引入跨行归约，但仍要确认没有随 batch 改核。
  • Prefix-shared attention：GRPO 里 G 条回复共享同一段 prompt，KV 算一次再复用，省的是重复 prefill。

多卡再锁：TP=1 与 TP>1 的累加顺序；CP 上 attention 的 (out, lse) 合并；通信用确定性 all-reduce / 自管 AG+RS，NCCL 只当搬运。

和 serving 的交界

vLLM 把 decode 做快。RL-Kernel 保证采样时记下的 logprob，训练还能复现。比较的是「给定同一条已采样序列的 teacher-forcing logπ」，不是比较采样过程本身。
