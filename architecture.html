本仓库怎么拆

RL-Kernel 是算子库，不是 RL 调度框架。调用方写 kernel_registry.get_op("linear_logp")，仓库负责在 CUDA / Triton / ROCm / PyTorch 里挑第一个能跑的实现。

三层里它占哪一层

层谁做本仓库有没有
编排verl、slime、vime、TRL没有。不拥有 dataset、reward I/O、macro 调度
引擎vLLM / sglang；Megatron / FSDP / DeepSpeed只有薄封装：rl_engine/executors/ 里的 sampler、trainer、weight bridge
算子本仓库有。logprob、GEMM、attention、packing、ratio/KL、GRPO loss

关掉 fused backend 时，registry 落到 PyTorch native，纯推理路径不受影响。

目录对应什么

路径角色
rl_engine/ Python 包。调用入口、registry、各后端 wrapper、executors、硬件探测。
rl_engine/kernels/ 算子 HAL。registry.py 按设备排优先级；ops/cuda、ops/triton、ops/rocm、ops/pytorch 是四套实现。
rl_engine/platforms/ DeviceContext：CUDA / HIP(ROCm) / CPU。决定走哪张 priority 表。
rl_engine/executors/ rollout、vLLM sampler、DeepSpeed trainer、zero-copy weight bridge、stateless reference/reward 前向。
csrc/ 编译进 rl_engine._C 的 CUDA/C++。ops.cpp 把 kernel 绑到 Python。

Python wrapper 不写矩阵乘法；它检查 dtype/形状、调 _C 或 Triton，失败就让 registry 试下一个 backend。

一次 get_op 怎么选核

  1. device_ctx 看 torch.cuda.is_available()，再用 torch.version.hip 区分 NVIDIA CUDA 和 AMD ROCm。
  2. KernelRegistry 取出该平台、该逻辑名的优先级列表。例如 CUDA 上 det_gemm 是 CUDA kernel → Triton；linear_logp 默认 Triton → PyTorch，Hopper 上再插入 SM90 fused linear logp。
  3. 按列表构造实例。构造成功就缓存。已经失败过的 backend 本进程不再试。
  4. 全部失败才报错。CPU 只有 PyTorch native。

逻辑名和文件不是一一对应。"logp" 吃已有 logits；"linear_logp" 从 hidden 和 LM head 权重算 selected logp；"batch_invariant_logp" / deterministic 变体锁归约顺序。调用方写逻辑名，不写 .cu 文件名。

CUDA、Triton、ROCm 不是三套 API。对外仍是 op(hidden, weight, target_ids)。换卡换的是 priority 表，不是训练脚本。

csrc 里有什么

setup.py 把 csrc/ 编成扩展 rl_engine._C。csrc/ops.cpp 声明并注册：

  • generic / SM90 fused logp
  • fused linear logp（TMA + tensor-core 前向，chunked 反向）
  • batch-invariant logp
  • det GEMM、deterministic attention、prefix-shared attention
  • RMSNorm、RoPE、embedding / LM head 的 SM90 路径

SM90 路径编译期用 KERNEL_ALIGN_FORCE_SM90 挡住；运行期还要看 compute capability。扩展没编出来时，CUDA wrapper 构造失败，registry 落到 Triton 或 PyTorch。

前向链和这些文件的关系

\[ \mathrm{embed}\to\mathrm{RMSNorm}\to\mathrm{GEMM}\to\mathrm{RoPE}\to\mathrm{Attn}\to\mathrm{MLP} \to\mathrm{LM\,head/linear\_logp} \]
块逻辑名典型 backend
Embedding / LM headembedding、lm_headPyTorch native；Hopper 上 SM90
RMSNormrms_normPyTorch 参考；CUDA kernel 在 csrc/cuda/rmsnorm.cu
矩阵乘det_gemmCUDA det GEMM → Triton；cuBLAS 参考不算 invariant
RoPEropeCUDA SM90 → Triton → PyTorch
Attentionattention、attn确定性 softmax CUDA；FlashAttention 是另一条生产路径
Logproblinear_logp / logp / batch_invariant_logp见上一页合同
目标ratio_kl、grpo_lossTriton → PyTorch

Executors：引擎边上的薄层

它们不替代 vLLM 或 DeepSpeed，只把本仓库的 op 接到 rollout / 训练边界：

模块做什么
executors/rollout.pyRolloutExecutor：选 logp backend、挂采样器、接权重更新。
executors/vllm_sampler.pyvLLM shared-prefix 采样。GRPO 同 prompt 多回复时复用 prefix cache。
executors/deepspeed_trainer.pyDeepSpeed 训练 worker，损失侧走 registry 里的 logp / GRPO op。
executors/bridge.py训练 → rollout 的权重桥（CUDA VMM / IPC / shared memory）。版本对不上，logprob 对齐没有意义。
executors/stateless_executor.pyReference / Reward 的无 KV 前向，避免和 decode cache 比错路径。

采样仍在引擎里；本仓库保证「记下的 old_logprob」和「训练侧重算的 logπ」走同一套算子合同。
